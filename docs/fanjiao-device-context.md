## 真实设备上下文的核对结论

1. 启动时最先使用旧上下文，约 1.433 秒后开始使用新上下文。
2. 新值在 `/user/init` 的**请求头**里就已经存在，不能把该接口的响应当作新值来源。
3. 完整记录中没有发现任何响应直接返回新旧设备值，也没有发现明显的数美设备初始化端点；这不排除本地处理、变换或未被 HAR 记录的通信。
4. 启动后用新旧值分别重新搜索，都成功。这次更新没有立即令旧值失效；有效期、跨设备可用性和长期更新规则仍未知。
5. 数美 SDK 是有官方资料与客户端字符串支持的主要线索，但还未得到 `sm_device` 与具体 SDK 方法之间的完整调用链证据。

因此当前不能把“读取 HAR 中的值”表述成“已经实现独立初始化”，也不能保证仅增加一个饭角 HTTP 初始化请求就能解决。

下表时间为北京时间 UTC+8；entry 为完整 HAR `log.entries` 的 0 基索引。A、B 是报告标签，不是设备值或它们的哈希。

| 时间 | entry | 事件 | 设备上下文 |

| 11:49:17.754 | 102 | 发送 `GET /walkman/api/recommend/banner` | A，92 字符，与早先成功搜索捕获值完全相同 |
| 11:49:18.581 | 102 | banner 响应完成 | 未直接返回 A/B |

`user/init` 响应含推广状态、实时通信/号码认证配置等字段，没有设备上下文返回字段。此 POST 只做离线分析，没有重放初始化、统计或播放历史写入。

已扫描完整 HAR 的响应文本，并对标为 base64 的响应解码后做比较，没有找到 A/B 的直接包含关系。不能据此排除响应经本地变换后参与生成，也不能证明抓包之外没有 SDK 通信。

## 4. SDK 线索与客户端核对

[饭角官方 SDK 清单](https://www.fanjiao.co/pages/sdk.html)明确列出数美 SDK，用途为风控，使用场景包含 App 启动。

[数美官方 Android 接入说明](https://github.com/ishumei/fp-android)描述：SDK 经 `create` 初始化，通过 `getDeviceId` 获取上下文；存在缓存时可先返回缓存值，并通过回调更新。接入参数包含组织、应用和公钥配置。这种机制与本次先 A 后 B 的时序吻合，但 SDK 通用文档不能证明饭角的具体实现或配置。

另外，从捕获的 `/app/version` 响应取得官方 Android 安装包地址，按 HTTP Range 读取 ZIP 目录、`classes.dex` 和 arm64 `libapp.so`，实际传输约 27.9 MB，没有下载完整 314.3 MB 包：

- `libapp.so` 可见 `initShumei` 与 `sm_device` 字符串。
- `classes.dex` 可正常解析，但仅 4 个类，含 `Lcom/stub/StubApp;` 加固入口；没有可直接审阅的 SDK 调用链。
- 版本接口声明的下载版本为 3.16.0，而本次抓包 UA 标记 3.15.1。没有把这份下载包认作与捕获完全相同的构建，字符串也可能属于未执行代码。

上述证据支持继续调查客户端 SDK 接入，不能证明数美 `getDeviceId` 的返回值未经转换就等于 `sm_device`，也不能据此推导生成算法。

## 5. 对 Folia 实现的影响

- 业务数据仍走 `Omni → provider/transport → Electron IPC → Node 饭角服务`。
- 主进程负责持有设备上下文和提供初始化状态；获取器必须有真实可用的来源，不能把随机 UUID 或固定 HAR 值当作完整实现。
- 设备上下文的获取方式需要单独核实：客户端 SDK、可用的官方 Web 初始化或正式服务接入方式。Android SDK 的存在不等于可直接在 Node.js 使用，也不证明另一个应用配置生成的值会被饭角接受。
- 完整 SDK 上下文的自动初始化和更新仍未完成；但公开搜索已验证不需要先完成这一项，采用最新搜索方案继续接入。播放与账号相关能力仍需独立核对。

若后续接口确实需要真实设备上下文，再检查与捕获对应的 SDK 调用及配置。现有网络证据无法单独得到完整初始化实现，但这不再阻塞已测试的公开搜索接入。
